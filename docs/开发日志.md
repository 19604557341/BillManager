### 技术决策与问题解决
- **枚举改造如何做到不改表、不影响前端**：`@EnumValue`（MyBatis-Plus）让读写数据库时使用 `code` 字段值，与现有 `VARCHAR(20)` / `TINYINT` 列完全兼容；`@JsonValue`（Jackson）让 JSON 序列化与反序列化同样走 `code` 值。两者配合后接口报文格式与改造前逐字节一致，前端无感知。
  - 踩坑记录：`@EnumValue` **只能标注在字段上**，标注在 getter 方法上会报"注解类型不适用于该声明类型"的编译错误。
  - `BillType` 的 `code` 在构造方法中直接取 `name()`，避免每个枚举常量重复书写一遍编码字符串。
- **为什么用 `.env` + `config.import` 而非纯环境变量**：纯环境变量方案要求为每个 IDE 运行配置单独设置变量，`mvnw test` 也需先注入环境；`spring.config.import` 方案在 IDE 直接运行与命令行测试下都自动生效。同时系统环境变量优先级**高于** `.env`，生产 / CI 仍可直接用环境变量，不依赖 `.env` 文件。
  - `optional:` 前缀保证缺失 `.env` 时不报"配置文件不存在"，但若此时 `DB_PASSWORD` 也未设置，占位符无法解析会让应用启动即失败——这是期望行为，避免静默使用空密码连接数据库。
  - `.env` 需按 properties 格式解析，故 import 位置用 `[.properties]` 扩展名提示。
- **关键发现：现有测试无法证明数据源可用**。改造后 `contextLoads()` 通过，但用**故意错误的密码**再跑一次，它**依然通过**。原因是 HikariCP 懒初始化，连接池直到首次 `getConnection()` 才建立，而该测试从不触发数据库访问。
  - 为真正验证，临时补了一个注入 `DataSource` 并调用 `getConnection()` 的测试：确认 `.env` 密码可用（`HikariPool-1 - Added connection`，`user=root@localhost`）；再注入错误的环境变量密码，得到 `Access denied for user 'root'@'localhost'`，反证系统环境变量优先级高于 `.env`。验证完毕后已删除该临时测试，并记为 TD-11。
- **凭据外置 ≠ 泄露已消除**。外置只保证此后不再写入仓库，早期提交中的明文 root 密码仍留在 git 历史里，且该历史已推送到远程。本项目已通过改用专用账户切断对 `root` 的依赖，但 **root 密码本身仍需轮换**——之所以暂缓，是因为同一 MySQL 实例上还承载 `bill`、`book` 两个库，贸然轮换会让那两个项目立即连不上，需先更新它们的配置。记为 TD-9。
- **专用账户的验证方式**：除 `SHOW GRANTS`、`SHOW DATABASES`（确认看不到 `bill` / `book`）外，还在事务内实测 INSERT / UPDATE / DELETE 后 `ROLLBACK`，既验证写权限可用，又不向含真实数据的表留下测试记录。随后启动应用实调 `GET /api/categories`（200，23 个启用分类）与 `GET /api/bills/page`（200，`total=4`），确认占位符解析正确、完整链路可用；其中 `total=4` 而表内 5 行，正好反证 `@TableLogic` 过滤生效，`billType` 返回 `"EXPENSE"` 字符串则反证 `@JsonValue` 序列化正常。
  - 踩坑记录：`mvnw spring-boot:run` 的后台 shell 可能先退出，把应用 JVM 留成孤儿进程继续占用 8080；清理时须先按命令行区分目标 JVM 与 IDE 自身的 JVM，避免误杀。

## 2026-09-23 账单模块（删除）

### 完成内容
- 删除账单接口 [`BillController.deleteBill()`](../src/main/java/com/example/billmanager/controller/BillController.java)：
  - `DELETE /api/bills/{billId}`：路径参数定位待删除账单，`@NotNull` 校验路径参数，账单不存在时由全局异常处理器统一返回错误响应。
  - 业务实现 [`BillServiceImpl.deleteBillById()`](../src/main/java/com/example/billmanager/service/impl/BillServiceImpl.java)：
    - 先查询账单存在性，不存在时抛出 404 业务异常。
    - 基于 `@TableLogic` 执行逻辑删除，MyBatis-Plus 自动将删除转换为 `UPDATE bill SET deleted = 1`，数据库记录保留，后续查询自动过滤已删除账单。
    - 检查 `deleteById` 返回的受影响行数，行数为 0（账单已被并发删除）时同样抛出 404 业务异常。

### 技术决策与问题解决
- **修复注释与实际行为不符的关键问题**：原 Service 接口与实现的注释写的是"执行物理删除""删除操作不可恢复"，但 [`Bill`](../src/main/java/com/example/billmanager/entity/Bill.java) 实体的 `deleted` 字段标注了 `@TableLogic`，实际执行的是逻辑删除；已修正 Controller / Service / ServiceImpl 三层的相关注释，避免误导后续维护者。
- **并发竞态防护**：原实现先 `selectById` 再 `deleteById`，两步之间账单可能被其他请求并发删除，此时删除影响行数为 0 但接口仍返回"删除成功"的假象；现通过检查受影响行数兜底，行数为 0 时按 404 处理。
- **清理 Service 接口层无效校验注解**：`BillService.deleteBillById()` 参数上的 `@NotNull` 不会生效（方法级校验需要实现类标注 `@Validated`，而 `BillServiceImpl` 未标注），且控制层已做同样校验，属于冗余误导；已移除该注解及对应导入。

## 2026-09-23 账单模块（新增与修改）

### 完成内容
- 新增账单接口 [`BillController.createBill()`](../src/main/java/com/example/billmanager/controller/BillController.java)：
  - `POST /api/bills`：接收账单表单数据，`@Valid` 触发 DTO 参数校验后调用业务层创建账单。
  - 新增请求参数 [`BillCreatedDTO`](../src/main/java/com/example/billmanager/dto/bill/BillCreatedDTO.java)：
    - `billAmount`：`@NotNull` + `@DecimalMin("0.01")` + `@Digits(integer=13, fraction=2)`，与数据库 `DECIMAL(15,2)` 精度对齐。
    - `billType`：`@NotBlank` + `@Pattern("INCOME|EXPENSE")` 限定取值。
    - `categoryId`：`@NotNull`；`remark`：`@Size(max=500)`；`billDate`：`@NotNull`。
  - 业务实现 [`BillServiceImpl.createBill()`](../src/main/java/com/example/billmanager/service/impl/BillServiceImpl.java)：
    - 新增前对分类进行三重业务校验：分类必须存在（404）、必须处于启用状态（400）、分类类型必须与账单类型一致（400）。
    - 账单 ID 由雪花算法自动生成，`createdTime` / `updateTime` 由 `MyMetaObjectHandler` 自动填充。
- 修改账单接口 [`BillController.updateBill()`](../src/main/java/com/example/billmanager/controller/BillController.java)：
  - `PUT /api/bills/{billId}`：路径参数定位账单，请求体携带修改后的数据。
  - 新增请求参数 [`BillUpdateDTO`](../src/main/java/com/example/billmanager/dto/bill/BillUpdateDTO.java)：字段与校验规则同 `BillCreatedDTO`。
  - 业务实现 [`BillServiceImpl.updateBillById()`](../src/main/java/com/example/billmanager/service/impl/BillServiceImpl.java)：
    - 先校验账单存在性（不存在抛 404），再执行与新增一致的分类三重校验，最后覆盖字段并更新。
    - 修改时间由 `MyMetaObjectHandler` 在更新时自动填充。

### 技术决策与问题解决
- **提前在业务层校验分类**：若直接落库，无效分类 ID 会触发数据库外键约束异常（表现为 500 系统错误）；提前校验可返回语义明确的业务错误提示（404/400）。
- **分类类型与账单类型强一致**：防止出现"收入账单挂支出分类"的脏数据。
- **修复 Controller 方法误写为 `private`**：Spring MVC 无法将请求映射到私有方法，`PUT /api/bills/{billId}` 会直接报错，已改为 `public` 并补充 `@NotNull` 路径参数校验。
- **修复修改账单的校验顺序问题**：原实现将"账单不存在"的判断放在分类校验之后，账单不存在时可能返回误导性的"所选分类不存在"错误；已调整为先校验账单存在性，再校验分类合法性。
- **清理 Service 接口层无效校验注解**：移除 `BillService` 接口方法参数上不会生效的 `@Valid`（参数校验统一由控制层触发），并补齐接口 Javadoc。

## 2026-09-14 账单模块（查询部分）

### 完成内容
- 新增账单实体 [`Bill`](../src/main/java/com/example/billmanager/entity/Bill.java)：
  - 主键采用雪花算法（`IdType.ASSIGN_ID`）。
  - 金额使用 `BigDecimal`，账单日期使用 `LocalDate`。
  - 通过 `@TableLogic` 实现逻辑删除（`deleted` 字段）。
  - `createdTime` / `updateTime` 通过 `@TableField(fill = ...)` 自动填充。
- 新增账单查询接口 [`BillController`](../src/main/java/com/example/billmanager/controller/BillController.java)：
  - `GET /api/bills/{billId}`：查询账单详情，账单不存在时抛出业务异常（404）。
  - `GET /api/bills/page`：分页查询账单列表。
- 新增分页查询参数 [`BillQueryDTO`](../src/main/java/com/example/billmanager/dto/bill/BillQueryDTO.java)：
  - 支持按账单类型、分类 ID、日期范围组合查询，所有条件均可选。
  - 页码最小为 1，每页数量限制在 1~100。
- 新增分页返回对象 [`BillPageVO`](../src/main/java/com/example/billmanager/vo/BillPageVO.java)：
  - 在账单字段基础上附加 `categoryName`，避免前端二次查询分类。
- 业务实现 [`BillServiceImpl.getBillPage()`](../src/main/java/com/example/billmanager/service/impl/BillServiceImpl.java)：
  - 使用 `LambdaQueryWrapper` 动态拼接查询条件。
  - 查询后提取当前页所有分类 ID，**批量查询**分类信息并组装为 Map，避免 N+1 查询问题。
  - 结果按账单日期、创建时间倒序排列。

### 技术决策与问题解决
- **分页插件**：在 [`MyBatisPlusConfig`](../src/main/java/com/example/billmanager/config/MyBatisPlusConfig.java) 中注册 `PaginationInnerInterceptor`（MySQL 方言），并设置单页最大条数 `maxLimit=100` 与 DTO 校验保持一致，防止恶意超大分页请求。
  - 踩坑记录：缺少分页拦截器时 `selectPage` 不会生成 LIMIT 子句，会查出全表数据且 `total` 恒为 0。
- **方法级参数校验异常**：Spring Framework 6.1+ 中，`@Validated` 类的 `@PathVariable` / `@RequestParam` 简单参数校验失败时抛出的是 `HandlerMethodValidationException` 而非 `ConstraintViolationException`，已在 [`GlobalExceptionHandler`](../src/main/java/com/example/billmanager/exception/GlobalExceptionHandler.java) 中单独处理。

## 2026-09-13 项目搭建与分类模块

### 完成内容
- 初始化 Spring Boot 项目（Spring Boot 4.1.1 / Java 25），引入依赖：
  - `spring-boot-starter-webmvc`、`spring-boot-starter-jdbc`、`spring-boot-starter-validation`
  - `mybatis-plus-spring-boot4-starter` 3.5.17、`mybatis-plus-jsqlparser`
  - `mysql-connector-j`、`lombok`、`spring-boot-devtools`
- 编写数据库初始化脚本 [`Sql.sql`](../src/main/resources/Sql.sql)：
  - `category` 分类表：含唯一索引 `uk_category_name_type (category_name, category_type)`，`status` 字段实现启用/禁用。
  - `bill` 账单表：金额 `DECIMAL(15,2)`，外键关联分类表，为 `bill_date`、`bill_type`、`category_id` 建立索引，`deleted` 字段支持逻辑删除。
  - 预置 15 个支出分类和 7 个收入分类作为初始数据。
- 完成分类模块全套接口 [`CategoryController`](../src/main/java/com/example/billmanager/controller/CategoryController.java)：
  - `GET /api/categories`：查询启用状态的分类列表，可按类型过滤，按类型 + 排序值升序。
  - `POST /api/categories`：新增分类，带参数校验。
  - `PUT /api/categories/{categoryId}`：修改分类，校验重名（排除自身）。
  - `DELETE /api/categories/{categoryId}`：删除分类（逻辑删除，置 `status=0`）。
- 基础设施搭建：
  - 统一响应格式 [`Result<T>`](../src/main/java/com/example/billmanager/vo/Result.java)（code / message / data）。
  - 业务异常 [`BusinessException`](../src/main/java/com/example/billmanager/exception/BusinessException.java) + 全局异常处理器 [`GlobalExceptionHandler`](../src/main/java/com/example/billmanager/exception/GlobalExceptionHandler.java)，统一处理参数校验异常与业务异常。
  - 字段自动填充 [`MyMetaObjectHandler`](../src/main/java/com/example/billmanager/config/MyMetaObjectHandler.java)：插入时填充 `createdTime` / `updateTime`，更新时填充 `updateTime`。
  - [`application.yml`](../src/main/resources/application.yml)：数据源、MyBatis-Plus 驼峰映射与 SQL 日志、devtools 热重启。

### 技术决策与问题解决
- **分类删除采用"禁用"而非物理删除**：账单表通过外键引用分类，物理删除会破坏历史账单数据；同时数据库唯一索引 `(category_name, category_type)` 会被已禁用分类占用。
- **禁用分类的重建策略**：新增分类时若发现同名同类型分类已存在——
  - 处于启用状态 → 抛出 409 业务异常"该分类已存在"；
  - 处于禁用状态 → 恢复启用并更新排序值，规避唯一索引冲突（见 [`CategoryServiceImpl.createCategory()`](../src/main/java/com/example/billmanager/service/impl/CategoryServiceImpl.java)）。
